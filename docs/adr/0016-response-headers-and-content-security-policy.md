# 0016 — Response headers, and a content security policy written at deploy time

- Status: accepted; the follow-up is done
- Date: 2026-09-08 (revised the same day, once the policy shipped)

## Context

A review of the deployed application found **no security response headers on
either origin**: no `Content-Security-Policy`, `Strict-Transport-Security`,
`X-Content-Type-Options`, `X-Frame-Options` or `Referrer-Policy` on the SPA, and
none on the API either.

The two origins have different constraints.

The **API** is an Azure Functions app, so it controls its own responses
completely. There was no reason for the omission beyond nobody having added
them.

The **SPA** is served from an Azure Storage static website. That hosting mode
serves blobs and **cannot set custom response headers at all**. There is no
configuration for it; the feature does not exist. So the headers are not
missing through oversight — the platform has no way to send them.

## Decision

**On the API, harden every response.** `Responses.Harden` adds `no-store`,
`nosniff`, `X-Frame-Options: DENY` and `Referrer-Policy: no-referrer` to every
JSON body the API produces, success and failure alike. `no-store` is the one
that earns its place: every body is permission data for a named site, and
without a directive nothing stops a proxy or the browser's back-forward cache
holding it after the user signed out.

**On the SPA, write the policy at deploy time.** The blocker was never the
policy, it was that a static `index.html` cannot know the API origin — and a
`connect-src` missing it does not harden sign-in, it breaks it. `deploy.ps1`
does know it, because it already writes `config.json` from the same deployment
outputs. So `New-ContentSecurityPolicy` builds the policy from `apiBaseUrl` and
`Set-ContentSecurityPolicy` replaces the tag in the built `index.html` before
upload.

`web/index.html` keeps a narrow placeholder — `object-src 'none'; base-uri
'self'` — which is safe unconditionally and is what a developer running
`npm run dev` gets. The deployment **throws if that tag is missing**, so a
change to the build cannot quietly ship an unprotected page.

The policy as deployed:

```
default-src 'self';
script-src 'self';
style-src 'self' 'unsafe-inline';
img-src 'self' data:;
font-src 'self' data:;
object-src 'none';
base-uri 'self';
form-action 'self' https://login.microsoftonline.com https://login.windows.net;
frame-src https://login.microsoftonline.com https://login.windows.net;
connect-src 'self' https://login.microsoftonline.com https://login.windows.net <the API origin>;
```

Three things about it are deliberate.

`script-src` stays exact. Vite emits an external module script and no inline
script, so no `'unsafe-inline'` and no nonce is needed — and a nonce could not
be used anyway, because it would have to change per response and this is a
static file.

`style-src` cannot be exact. The tree indents rows and the progress bar sets its
width through the `style` attribute, which CSP counts as inline style. Style
injection is a far smaller problem than script injection, and accepting it here
is what keeps `script-src` strict.

`login.windows.net` is included alongside `login.microsoftonline.com` because
some tenants are redirected there during sign-in. Naming both costs nothing;
discovering the omission costs a broken sign-in in production.

**`frame-ancestors` and HSTS remain unavailable.** Both are ignored in a meta
tag. Serving them needs Azure Front Door or a CDN in front of the storage
account, which adds a resource, a cost and a second place for the origin to be
configured. Not taken.

## Consequences

A wrong policy breaks the application for everyone at the moment of deployment,
and CSP is enforced by the browser so no amount of server-side testing proves
it. Two things make that survivable: the policy is generated by a function
rather than typed into a file, so it is the same everywhere and can be inspected
before upload; and the deployment prints it. **A deployment that changes the
policy should be followed by one real sign-in**, and the rollback is to redeploy
the previous commit.

Clickjacking is still prevented in JavaScript rather than by a header:
`web/src/main.tsx` mounts React only when `window.self === window.top`, so the
application renders as a blank page inside a frame. That was added to stop
MSAL's hidden renewal iframe from booting a second copy of the app, and it
happens to be an effective frame guard. It is weaker than
`frame-ancestors 'none'` because it depends on the script running, and it is the
reason option 2 above stays on the table.

HSTS is absent, which matters less than it looks: the storage account sets
`supportsHttpsTrafficOnly`, so the HTTP endpoint refuses the connection rather
than serving anything over it. The residual risk is the first request of a
session on a hostile network.
